# OptiBed: Project and Implementation Guide

## 1. Project at a glance

OptiBed is an educational simulation of hospital bed allocation. It models a fixed-size hospital, a queue of patients with changing severity, random arrivals, emergency cases, treatment stays, and an episode reward. A tabular Q-learning agent learns an allocation policy: at each decision it chooses how many waiting patients to admit to currently available beds.

The repository has two ways to use the same simulation:

1. A Streamlit web dashboard that trains the agent and automatically plays out an episode.
2. A FastAPI service that exposes the simulation state and accepts an allocation from an external caller or agent.

The project is a compact Python application; it does not have a database, frontend build system, separate persistent model artifact, or deployment configuration in the checked-in files. The simulation and learner are implemented locally in Python.

> **Important:** This is a toy/teaching environment, not a clinical decision-support system. Its rules, rewards, and learned policy are not validated for real care decisions.

## 2. Repository layout

| Path | Responsibility |
|---|---|
| `rl_model.py` | Domain types, episode configuration, hospital simulation, reward and history calculation, and the tabular Q-learning agent. This is the shared backend used by both interfaces. |
| `app.py` | Streamlit dashboard, agent training/caching, simulation controls, patient and bed visualization, transition explanation, and charts. |
| `api.py` | FastAPI application and HTTP routes for health, reset, state, stepping, and grade. |
| `tests/test_environment.py` | Unit and HTTP-level tests for the environment rules, learning behavior, determinism, and API validation. |
| `requirements.txt` | Runtime/test package names: NumPy, Streamlit, pandas, FastAPI, and Uvicorn. |
| `README.md` | Short product description, run instructions, rules, rewards, and API route summary. |
| `__pycache__/` | Python-generated bytecode cache; not application source. |

The repository does not include a separate package directory or project/build manifest. The modules import one another directly (`app.py` and `api.py` both import `rl_model.py`).

## 3. Technology and dependencies

- **Python** is used for the simulation, learning algorithm, dashboard, API, and tests.
- **NumPy** provides seeded random number generation, Poisson arrivals, random choices, and the grade calculation.
- **Streamlit** renders the interactive dashboard and maintains browser-session UI state.
- **pandas** converts the simulation history into chart-ready data.
- **FastAPI** defines the HTTP service and OpenAPI documentation.
- **httpx2** provides the transport used by FastAPI's `TestClient` in the test suite.
- **Pydantic** (used through FastAPI) validates API request bodies and query parameters.
- **Uvicorn** serves the FastAPI application.
- **`unittest`**, `unittest.mock`, and FastAPI's `TestClient` are used for the tests.

There is no database or external queue, no authentication layer, no external RL framework, and no model file loaded from disk. The Q-table is learned in memory when the Streamlit app starts.

## 4. Core domain model (`rl_model.py`)

### Configuration

`Task` describes the bed count, initial patient count, episode length, and regular arrival rate. `STANDARD_TASK` is the active scenario:

| Setting | Value |
|---|---:|
| Beds | 8 |
| Initial waiting patients | 8 |
| Episode length | 5 steps |
| Regular arrivals | Poisson distribution with rate 1.5 per step |

Reward amounts and event probabilities are module-level constants. The environment currently uses this one standard task by default; callers may replace `environment.config` directly in code (as tests do), but the HTTP API does not expose task configuration.

### Patient and observation types

Each internal `Patient` has an integer ID, a severity (`low`, `medium`, or `high`), an emergency flag, and a remaining treatment stay. `Patient.observe()` exposes only ID, severity, and emergency status.

An `Observation` returned by the environment contains:

- `beds`: beds currently available;
- `patients`: the waiting queue, each as an observation;
- `step` and `max_steps`: episode progress;
- `done`: whether the 5-step episode has completed.

Patients occupying beds are intentionally not included in the waiting-patient list. Their count is reflected by available beds. `StepInfo` provides additional transition details such as the selected patients, arrivals, occupied-bed count, and individual reward components.

### Reset, seeding, and reproducibility

Constructing `HospitalEnvironment(seed=...)` initializes a NumPy random generator and calls `reset()`. Reset clears the episode, creates the initial queue, resets the ID counter and reward total, and records a step-zero history row. Passing the same seed reproduces the same initial patients and random sequence. A reset without a new seed reuses the environment's current seed.

## 5. How one environment step works

`HospitalEnvironment.step(allocate)` receives the number of waiting patients to treat. The allocation must be an integer, cannot be negative, and cannot exceed either available beds or queue length. Invalid actions fail before the step counter advances. A completed episode rejects further steps until reset.

After validation against the beds available at the start of the step, the implementation proceeds in this order:

1. Record beds available before discharges, then advance stays for patients already occupying beds and discharge those whose remaining stay reaches zero.
2. Select the requested number of patients from the waiting queue.
3. Give each selected patient a randomly sampled stay of 1, 2, or 3 steps and move them into occupied beds.
4. Add treatment rewards and the emergency treatment bonus for treated patients.
5. Penalize waiting high-severity and emergency patients, penalize beds left idle while patients wait (counting only beds already free before discharges), and probabilistically worsen waiting patients who are not already high severity.
6. Generate regular and emergency arrivals, except after the final decision of an episode.
7. Advance the step counter, sum reward components, update cumulative reward and history, and return the next observation, reward, completion flag, and transition details.

Treatment selection sorts the waiting queue by emergency status, then severity, then patient ID (earlier IDs win ties). Consequently, emergencies are preferred to non-emergencies, and within those groups high severity is preferred to medium and low.

### Arrival and deterioration rules

- Each non-final step generates a Poisson-distributed number of regular arrivals at rate 1.5.
- Independently, there is a 20% chance of one emergency arrival on a non-final step.
- Regular patient severity is sampled as low 50%, medium 30%, or high 20%.
- An emergency is always high severity.
- A waiting low- or medium-severity patient has a 20% chance per step of worsening by one level. A high-severity patient remains high.
- An admitted patient's stay is sampled uniformly from 1 through 3 steps (integer values).

### Reward model

The step reward is the sum of these components:

| Event | Reward |
|---|---:|
| Treat low / medium / high patient | +1 / +2 / +3 |
| Treat an emergency patient | +1 additional bonus |
| Each untreated high-severity patient | -2 |
| Each untreated emergency patient | -1.5 additional penalty |
| Each idle bed while someone waits (up to the queue size) | -0.3 |
| Each severity worsening event | -0.5 |

An untreated emergency patient is also high severity, so both the high-severity and emergency penalties apply. In the final step there are no new arrivals, but normal treatment, waiting penalties, and deterioration calculations still occur.

The `grade()` method maps cumulative raw reward through a logistic transformation scaled by the episode length, clipping the normalized return before mapping it into approximately `[0.001, 0.999]`. It is a bounded presentation/API score, not a clinical or statistical quality measure.

### History

The environment appends a history row at reset and after every step. Rows include total waiting patients and severity counts, emergency queue count, occupied and available beds, regular/emergency arrivals, step reward, cumulative reward, and each reward component. The dashboard's Graphs tab uses these rows; the API does not currently expose the history endpoint.

## 6. Q-learning agent

`QLearningAgent` learns a state/action value table from repeated simulations of `HospitalEnvironment`.

### State representation

The learner compresses the full observation into a six-integer key:

1. available beds;
2. waiting high-severity count;
3. waiting medium-severity count;
4. waiting low-severity count;
5. waiting emergency count;
6. steps remaining.

Each queue count is capped at 16 (`2 * STANDARD_TASK.beds`). This bounds the tabular state space. The key deliberately excludes individual patient IDs and ordering, as well as the remaining stays of occupied patients; two different full situations can therefore map to the same learning state.

### Actions and policy

An action is an integer from zero through `min(available beds, waiting patients)`, inclusive. During training, epsilon-greedy exploration selects a random valid action with a probability that decays linearly from 0.35 to a floor of 0.03 over the configured training episodes. Otherwise the agent selects the action with the largest stored Q-value. Ties are resolved in favor of the larger allocation.

During dashboard playback the agent starts with a copy of the trained Q-table
and chooses greedy actions. After every executed transition it performs one
online Q-learning update. The shared cached trained model remains unchanged;
each Streamlit session gets its own mutable copy.
Reset restores that session's copy from the frozen post-training Q-table.

### Update and defaults

The defaults are 1,200 training episodes, learning rate (`alpha`) 0.15, discount factor (`gamma`) 0.95, and learner seed 2026. The standard one-step update is:

```text
Q(s, a) <- Q(s, a) + alpha * (r + gamma * max_a' Q(s', a') - Q(s, a))
```

For terminal transitions, the target is just the immediate reward (there is no next-state value). Each training episode gets environment seed `agent_seed + episode`; a separate seeded generator controls exploration. This makes training repeatable for a fixed configuration and seed. `episode_returns` stores the sum of rewards for each training episode, and `q_table` maps state keys to action values.

The Q-table is held in process memory. The Streamlit app uses `st.cache_resource` to train/cache one shared agent for the running app process, so it is not retrained on every rerun. Training parameters are constructor options in Python, not dashboard settings. Training also records per-episode return and its trailing-100 mean and sample standard deviation, epsilon, observed exploration-decision rate, transition count, learned-state count, state-action value count, and mean tried actions per state. A copy of the Q-table is retained at the midpoint of training alongside the final table.

## 7. Streamlit dashboard (`app.py`)

### Startup

The app sets a wide page layout, defines CSS and a small inline bed SVG, then gets the trained learner through a cached resource function. It initializes the current environment and UI state in `st.session_state`:

- `environment`: the active episode;
- `simulation_running`: whether automatic playback is on;
- `last_step_time`: timing reference for the playback interval;
- `last_step`: data for the most recent transition explanation.

The first app load includes model training (1,200 episodes by default). Streamlit reruns reuse the cached agent resource.

An agent overview is displayed below the OptiBed title and episode description,
including the algorithm, training episode count, trained-state count, recent
training return, and playback interval.

### Simulation tab

The Simulation tab displays:

- Start, Stop, and Reset controls;
- bed availability, waiting queue size, cumulative reward, and grade;
- progress through the 5-step episode;
- equally sized, equal-height hospital-bed and waiting-patient panels with
  responsive layouts;
- bed icons annotated with the currently occupying patient's ID, severity, and
  emergency status; these details disappear when the environment discharges that
  patient;
- spacious severity-colored user-icon patient cards; non-emergency cards omit a
  redundant waiting badge, and an empty queue uses a subdued empty state;
- the most recent observation, selected allocation, Q-value, reward breakdown, treated patients, next observation, and arrivals.
- a per-step table of allocation, gross reward, penalty, net result, and reward-component details.

When running, a Streamlit fragment reruns frequently to keep the UI responsive, but a decision is made only after the 1.8-second playback interval has elapsed. Start enables automatic greedy actions; Stop pauses them; Reset makes a new environment and clears the displayed last transition.

Before the first decision, the dashboard leaves the transition area clear rather
than showing a separate prompt banner.

### Graphs tab

The Graphs tab converts `environment.history` to a pandas DataFrame and displays:

- waiting patients by high, medium, and low severity;
- occupied versus available beds;
- step reward versus cumulative episode reward;
- the current episode grade.

The charts label the simulation step on the horizontal axis and identify the
count or reward quantity on the vertical axis; Streamlit's native series
legends distinguish each line. Before the first step the tab shows a prompt
instead of empty charts. The graph fragment refreshes while playback is running.

The Training tab displays training metrics and hyperparameters, one frozen
Q-table captured immediately after training, and the executed-step Q-learning
updates with gross reward, penalty, and final net result. The post-execution
Q-table and training charts are not displayed. The frozen table, training
metrics, and execution updates can be downloaded as CSV.

## 8. HTTP API (`api.py`)

The API exposes the same `HospitalEnvironment` class, but it does not call the Q-learning agent. A caller submits its own allocation via `/step`.

| Method and route | Input | Response / behavior |
|---|---|---|
| `GET /health` | None | `{"status":"ok"}` health response. |
| `POST /reset?seed=<nonnegative integer>` | Optional query parameter | Replaces the active environment with a fresh episode and returns its initial observation. |
| `GET /state` | None | Returns the current observation. |
| `POST /step` | JSON object such as `{"allocate": 2}` | Advances the simulation; returns `observation`, `reward`, `done`, and `info`. |
| `GET /grade` | None | Returns normalized `grade`, raw cumulative reward, and current step. |

`StepRequest` forbids unknown fields and requires `allocate` to be a strict integer greater than or equal to zero. Environment-level upper-bound failures are translated to HTTP 422. Attempting to step after completion is translated to HTTP 409. FastAPI publishes interactive OpenAPI documentation at `/docs` when the service is running.

### API state ownership

`api.py` creates one module-global `environment`. All requests handled by that application process operate on it, and `/reset` replaces it for all callers. There is no per-user session identifier or storage layer. This is convenient for a local demo or a single external agent, but concurrent independent users would share and affect the same episode; a multi-user deployment would need explicit session/state isolation.

## 9. Running the project

From the `Rl-Project` directory:

```powershell
python -m pip install -r requirements.txt
python -m streamlit run app.py
```

The Streamlit URL is printed by the CLI. To run the API separately:

```powershell
python -m uvicorn api:app --reload
```

The API is typically available at `http://127.0.0.1:8000`, with interactive documentation at `http://127.0.0.1:8000/docs`.

Run the tests from the same project directory:

```powershell
python -m unittest discover -s tests -v
```

## 10. Test coverage and review notes

`tests/test_environment.py` contains 14 tests covering:

- standard scenario settings, repeatable reset, and history rows;
- emergency/severity prioritization and reward breakdown;
- deterioration and emergency arrivals;
- penalties for untreated high-severity/emergency patients and unused beds;
- action validation without episode advancement;
- bed release after a stay;
- grade bounds and monotonic behavior;
- Q-learning training, valid actions, and fixed-seed reproducibility;
- API health/reset/state/grade/step behavior and invalid request rejection.

The suite was run while preparing this guide: **14 tests passed**.

The following are useful constraints to keep in mind when extending or deploying the project:

1. **This is a simplified simulator.** Arrival rates, deterioration, stays, and rewards are fixed assumptions in code; they do not represent validated real-world clinical rules.
2. **The learner is intentionally compact.** Counts are capped, and patient identity/order and occupied-patient remaining stays are not features of the Q-state. This reduces the table but loses information about the true environment state.
3. **API episodes are shared.** The module-global environment has no per-client isolation, persistence, authentication, or concurrency/session management.
4. **Training is in-memory and app-startup work.** There is no saved model artifact or dedicated training command in the repository. A process restart requires training again.
5. **Environment timing and allocation constraints are step-based.** A submitted allocation is validated against currently reported available beds before existing stays are advanced inside the transition. Clients should use the returned observation as the authority for their next action.
6. **Dashboard and API are separate entry points.** The dashboard uses the trained policy; the API accepts external decisions. Starting one does not make the other call into it.

These are current design properties and scope limitations, not claims that the prototype is production-ready.
